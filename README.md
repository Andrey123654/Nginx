# NGINX Scope — аудит публикаций Nginx

![NGINX Scope](web/static/og.jpg)

Веб-сервис принимает `nginx.conf`, сохранённый вывод `nginx -T` или многофайловую выгрузку с разделителями `==> /путь/file.conf <==` и формирует отчёт о мисконфигурациях. HTTP- и `stream`-публикации распознаются отдельно: проверки заголовков, `location`, Host и HTTP rate limit не применяются к TCP/UDP listener. Для каждого замечания приводится рекомендация, а кнопка «Исправленный конфиг» скачивает консервативно усиленный вариант. Тип определяется по содержимому: допускается текст UTF-8 до 5 МБ, бинарные данные блокируются. При добавлении реестра DNAT `.xlsx`, `inventory.json` и результатов внешнего/внутреннего датчиков сервис показывает фактические адреса и области сетевой видимости. Постоянное хранение загруженных файлов отсутствует.

При отказе интерфейс показывает точную причину, имя файла, код ошибки и рекомендацию: превышение размера, бинарное содержимое, неверную кодировку, отсутствие файла, неподдерживаемый JSON или ошибку структуры inventory/датчика.

Для базового анализа обязателен только файл конфигурации Nginx. `inventory.json`, внешний и внутренний `sensor.json` необязательны и добавляются только когда требуется отчёт об адресах и областях видимости.

## Реестр внешних публикаций XLSX

Поле «Внешние публикации» принимает `.xlsx` с колонками `ID правила`, `Тип`, `Источник / Интерфейс`, `Внешний порт`, `Внутренний IP`, `Внутренний порт`, `Протокол`. Дополнительная колонка `№ п/п` допускается и игнорируется. Поддерживаются TCP, UDP и `Any`; внешняя сеть может быть указана в имени интерфейса в виде `203.0.113.0-24` или `203.0.113.0/24`.

Книга читается без выполнения формул и внешних ссылок; макросы, повреждённые архивы, более 10 000 строк и подозрительно большой распакованный размер отклоняются. Точные `listen IP:порт` сопоставляются с DNAT по IP, порту и протоколу. Wildcard-listen сопоставляется только при единственной паре порт/протокол; неоднозначность отображается как отдельное замечание и не подтверждает внешнюю видимость автоматически.

Повторяющиеся срабатывания одного правила группируются в общей таблице отчёта с числом повторений и затронутых объектов. В карточке каждой публикации остаётся подробная локальная аналитика.

Каждый блок `server` отображается отдельной карточкой: краткая справка-резюме, полный фрагмент настроек, `location`, listener, upstream, потенциальная зона по адресу прослушивания, фактическая зона и адреса по датчикам, локальная оценка и рекомендации. Для каждого `location` объясняются порядок выбора, назначение и влияние найденных директив; отдельная справка раскрывает смысл `listen`, `server_name`, TLS, upstream и журналирования. Кнопка «Сохранить эталон» создаёт `nginx-baseline.json` без сырого конфига. При загрузке эталона сервис показывает добавленные, удалённые и изменённые публикации с изменившимися полями.

Кнопка «Полный PDF» выгружает оформленный многостраничный отчёт с нумерацией страниц, сводкой, всеми замечаниями и рекомендациями, карточками публикаций, пояснениями `location`, фрагментами конфигурации, областями видимости и сравнением с эталоном.

Кнопка «SARIF для CI/CD» формирует SARIF 2.1.0 для GitHub Code Scanning и других совместимых систем. Результаты содержат правило, уровень, строку блока `server`, рекомендацию, свидетельство и ссылку на основание проверки.

PDF формируется на сервере в памяти и не сохраняется постоянно. Для кириллицы установщик Ubuntu и Docker-образ устанавливают `fonts-dejavu-core`. Если используется собственный reverse proxy, разрешите до 16 МБ для `POST /api/export/pdf`, поскольку структурированный отчёт содержит фрагменты публикаций. Для объединённых выгрузок `nginx -T` задайте для `/api/` значения `proxy_read_timeout 180s`, `proxy_send_timeout 180s` и `send_timeout 180s`: конфиг с тысячами публикаций может анализироваться дольше стандартных 30 секунд.

Начиная с версии 1.5.2 большие фрагменты `server` и `location` автоматически разбиваются по страницам PDF. Это предотвращает HTTP 500 для публикаций с сотнями или тысячами строк настроек.

Ошибка Firefox `NetworkError when attempting to fetch resource` при файле меньше 5 МБ обычно означает, что reverse proxy закрыл соединение по тайм-ауту, а не что расширение файла запрещено. Обновите конфигурацию из `deploy/nginx-scope.conf.example`, выполните `nginx -t` и reload.

## Практики Gixy и аналогичных проектов

Встроены независимо реализованные проверки классов ошибок из [Yandex Gixy](https://github.com/yandex/gixy) и актуального [Gixy-Next](https://github.com/MegaManSec/Gixy-Next): SSRF через динамический адрес `proxy_pass`, подмена Host, HTTP response splitting, перекрытие наследуемых `add_header`, traversal при несогласованных `location`/`alias`, неполный IP-allowlist и небезопасное использование `valid_referers`. Пакеты Gixy не являются runtime-зависимостью сервиса; исходный код сторонних проектов не копировался.

Из официального Nginx Analyzer взят принцип минимизации конфиденциальных данных: сервис не сохраняет конфиги, а эталон содержит только нормализованные свойства и хеши. Из Gixy-Next взяты воспроизводимый машинный формат и привязка правил к строкам. Автоматические исправления остаются консервативными: изменения, способные поменять маршрутизацию или ACL, выдаются как ручные действия.

## Веб-интерфейс

Локальный запуск:

```sh
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
uvicorn web.app:app --host 0.0.0.0 --port 8080
```

Откройте `http://<IP-СЕРВЕРА>:8080`. Сервис слушает все IPv4-интерфейсы; ограничьте порт корпоративной подсетью через firewall и используйте HTTPS reverse proxy для production. Развёртывание на Ubuntu Server 26.04 LTS описано в [docs/UBUNTU_DEPLOYMENT.md](docs/UBUNTU_DEPLOYMENT.md). Доступны Docker Compose и hardened systemd unit.

Готовый каркас для регулярной проверки ресурсов из двух точек наблюдения:

- `external` — датчик вне корпоративной сети;
- `internal` — датчик внутри корпоративной сети;
- локальная проверка вывода `nginx -T` без передачи полной конфигурации в отчёт;
- сводный JSON, CSV и автономный HTML-отчёт с фактической и ожидаемой зоной видимости.

Активные проверки ограничены allowlist из `inventory.json`, низкой частотой запросов и безопасным профилем. Используйте только для ресурсов, на проверку которых у вас есть разрешение.

## Быстрый старт

1. Скопируйте пример инвентаризации:

   ```sh
   cp inventory.example.json inventory.json
   ```

2. Укажите реальные URL, владельцев и ожидаемую видимость (`external`, `internal` или обе зоны).

3. На внешнем и внутреннем датчиках установите `httpx`, `nuclei` и `testssl.sh`. Опционально установите Docker для пассивного OWASP ZAP. Получайте бинарные файлы из доверенного корпоративного репозитория, проверяйте подписи/sha256 и фиксируйте одобренные версии.

4. Выполните в каждой зоне:

   ```sh
   ./bin/run-sensor.sh external inventory.json artifacts/external
   ./bin/run-sensor.sh internal inventory.json artifacts/internal
   ```

5. Соберите сводный отчёт:

   ```sh
   python3 audit.py aggregate \
     --inventory inventory.json \
     --input artifacts/external/sensor.json \
     --input artifacts/internal/sensor.json \
     --output reports
   ```

Откройте `reports/report.html`. Для CI код возврата равен `2`, если найдена незапланированная публикация или нарушение с уровнем `high`/`critical`.

## Проверка конфигурации Nginx

Команду следует запускать на самом reverse proxy. Полная конфигурация может содержать секреты, поэтому она обрабатывается потоком и не сохраняется:

```sh
sudo nginx -T 2>&1 | python3 audit.py nginx-config \
  --source edge-proxy-01 \
  --output artifacts/nginx-edge-proxy-01.json
```

Затем добавьте файл к агрегации:

```sh
python3 audit.py aggregate --inventory inventory.json \
  --input artifacts/external/sensor.json \
  --input artifacts/internal/sensor.json \
  --nginx-input artifacts/nginx-edge-proxy-01.json \
  --output reports
```

Статическая проверка контролирует, среди прочего: `server_tokens`, старые TLS-протоколы, `autoindex`, HSTS и основные защитные заголовки, небезопасный `alias`, открытые status/debug endpoints и наличие catch-all/default server. Это эвристики; находки требуют подтверждения владельцем ресурса.

Методическая привязка к документу ФСТЭК России от 12.04.2026, CIS NGINX Benchmark, NIST SP 800-128 и OWASP WSTG приведена в [docs/CONTROL_MAPPING.md](docs/CONTROL_MAPPING.md).

Исправленный вариант автоматически применяет только предсказуемые изменения: TLS 1.2/1.3, `server_tokens off`, `autoindex off`, базовые защитные заголовки, HSTS только в TLS-vhost и HTTP catch-all. CSP, пути `alias` и allowlist для `stub_status` оставляются ручными действиями, потому что они зависят от приложения и сети. Перед заменой рабочего файла обязательно выполните:

```sh
sudo nginx -t -c /путь/nginx.corrected.conf
```

Затем сравните конфигурации, проверьте сервис на тестовом окружении и только после этого выполните reload. Автоисправление не является заменой ревью владельцем ресурса.

## Модель данных и правила

Каждый ресурс имеет стабильный `id`, URL, владельца, критичность и ожидаемые зоны. Для split-horizon DNS можно задать ожидаемые CIDR отдельно для каждой зоны. Фактическая видимость считается только при успешном TCP/HTTP(S)-ответе из соответствующего датчика; один DNS-ответ публикацией не считается.

Основные состояния:

- `compliant` — фактическая видимость совпадает с ожидаемой;
- `unexpected_exposure` — ресурс доступен из зоны, где его не должно быть;
- `missing_exposure` — ресурс недоступен из требуемой зоны;
- `address_drift` — адрес публикации вышел за ожидаемые CIDR;
- `unknown` — отчёт нужного датчика отсутствует или устарел.

Секреты не помещайте в inventory. Для аутентифицированных проверок используйте отдельное хранилище секретов и краткоживущую учётную запись только для чтения.

## Эксплуатация

- Размещайте датчики в реально разных сетевых сегментах. Внешний датчик не должен использовать корпоративный VPN или внутренний DNS.
- Запускайте проверку после изменения публикации и по расписанию (например, каждые 6 часов).
- Передавайте артефакты между зонами через ваш CI или защищённое объектное хранилище.
- Закрепляйте версии/sha256 инструментов в корпоративном репозитории артефактов и обновляйте их контролируемо.
- Для ZAP задайте образ с фиксированным digest: `ENABLE_ZAP=1 ZAP_IMAGE='zaproxy/zap-stable@sha256:…' ./bin/run-sensor.sh …`.
- Отправляйте `report.json` в SIEM, а `summary.csv` — владельцам сервисов.
- Срок хранения сырых результатов ограничьте; HTML/JSON не должны содержать тела HTTP-ответов.

## Состав

- `audit.py` — встроенный безопасный датчик, анализатор Nginx и генератор отчёта;
- `web/pdf_report.py` и `web/sarif_report.py` — полные PDF- и SARIF-отчёты;
- `bin/run-sensor.sh` — оркестрация готовых утилит;
- `config/nuclei.yaml` — ограниченный профиль Nuclei;
- `inventory.example.json` — схема инвентаризации на примере;
- `tests/` — тесты классификации и анализа конфигурации.
